# DFBHD 断肢（dismember）崩溃分析与二进制补丁报告

目标：《Delta Force: Black Hawk Down》(三角洲特种部队6：黑鹰坠落)
可执行文件：`DFBHD.exe` V1.5.0.5（2,547,712 字节，x86 PE，ImageBase `0x400000`）
分析工具：REA (Ghidra 12.1.4 provider) + 手工反汇编崩溃 dump

---

## 一、背景

在 `items.def` 中删除有机体单位的 `nodismember` 属性即可开启断肢效果
（ITEM.TXT：`/nodismember /organic can be dismembered`）。
但该功能是半成品：删除属性后游戏会在多处因**缺少判空**而触发访问违例（Access Violation）。

本报告记录了两次实际崩溃的完整定位过程与对应的二进制补丁（补丁1 + 补丁2），
合并后的成品为 `DFBHD_patched.exe`。

### 偏移换算

PE 头中 `.text` 段 `VirtualAddress == PointerToRawData == 0x1000`，因此：

```
文件偏移 = VA − 0x400000
```

### items.def 标志解析（已确认）

- 解析函数：`FUN_00464350`（0x464350–0x466A46）
- `0x465EED` 处引用字符串 `"NoDismember"`（VA `0x63AD74`），命中则置位
  `def+0x34 |= 0x8000000`
- def 记录步长 `0x7B8`；`def+0x20` 为 8 字节名称串；`def+0x38` 为 unit_type 整数

### 运行时对象结构（已确认）

| 偏移 | 含义 |
|---|---|
| `obj+4` | → T（模型记录） |
| `T+0x20` bit0 | 断肢门控标志（与 def+0x34 的 0x8000000 对应） |
| `T+0x38` | → M（部件/断肢子记录，**由模型文件决定，items.def 无法控制**，可能为 NULL） |
| `M+0x180` | 容器回指指针 |
| `M+0x13C` | 与常量 `0x7E`(126) 比较的状态字段 |
| `obj+0x24` | → def 记录 |

> 关键结论：崩不崩取决于**模型是否带部件记录（T+0x38 是否为 NULL）**，
> 与 items.def 里写什么属性无关。非有机体单位本来就没有 `nodismember`，
> 只有有机体删除该属性才会进入这些脆弱的代码路径。

## 二、崩溃 1：附件移除例程缺判空

### dump 特征

```
Access violation at 0040DA6Ah, reading 0000013Ch
EAX = 00000000h
```

读地址 = `EAX + 0x13C`，且 EAX = 0 → 典型的 `[NULL+0x13C]`。

### 定位

崩溃位于 `FUN_0040d9f0`（0x40D9F0–0x40DAE7，附件移除例程），调用者为
`FUN_0040d880`（销毁循环，堆栈返回地址 `0x40d8cb` 吻合）。Ghidra 伪代码核心：

```c
iVar2 = *(int *)(iVar5 + 4);          // T = obj+4
if (((iVar2 != 0) && ((*(byte *)(iVar2 + 0x20) & 1) == 0)) &&   // 未设 nodismember
    (*(int *)(*(int *)(iVar2 + 0x38) + 0x13c) == 0x7e)) {       // ← 未判 [T+0x38] 是否为 NULL!
    bVar3 = true;
}
```

崩溃指令（0x40DA6A 起）：`83 B8 3C 01 00 00 7E` = `cmp dword ptr [eax+0x13C], 0x7E`，
其中 EAX = `[T+0x38]` = NULL。

### 补丁 1

在 hook 点 `0x40DA6A` 处用 5 字节 `E9 rel32` 跳转到 code cave，
cave 先 `test eax,eax / je` 判空，非空再执行原 `cmp` 逻辑。

- **hook**：raw `0x0DA6A`（VA `0x40DA6A`）原 5 字节 `83 B8 3C 01 00` → `E9 C3 6E 1D 00`（跳 `0x5E4932`）
- **cave**：raw `0x1E4932`（VA `0x5E4932`，利用 .text 末尾全零空洞），28 字节：

```
85 C0                       test eax, eax
74 13                       je   +0x13          ; NULL → 跳过比较
81 B8 3C 01 00 00 7E 00 00 00                   ; cmp dword [eax+0x13C], 0x7E
75 07                       jne  +7             ; 不等 → 走原路径续点
C7 45 F8 01 00 00 00        mov dword [ebp-8], 1
E9 2C 91 E2 FF              jmp  0x40DA7A       ; 原 cmp 之后的续点
```

## 三、崩溃 2：断肢对象生成返回 NULL 未判空

换上补丁 1 的 exe 后再次崩溃。

### dump 特征

```
Access violation at 00402FC9h
Attempting to write from 00000104h
EAX = 00000000h, EBX = fffdf7ffh
```

写地址 = `EAX + 0x104`，EAX = 0 → `[NULL+0x104]`。
EBX = `fffdf7ff` = `~0x208`（肢体掩码取反），与代码语义吻合。

### 定位

崩溃位于 `FUN_00402ca0`（0x402CA0–0x40301C，死亡/伤害处理）的断肢生成块：

```c
if ((((DAT_009f2190 != 0) && ((*(uint *)(param_1 + 0x20) & 1) == 0)) &&
    (iVar2 = *(int *)(iVar2 + 0x38), 0 < iVar2)) &&
   ((((*(uint *)(*(int *)(param_1 + 0x24) + 0x34) & 0x8000000) == 0 && ...
// switch 构建肢体掩码 uVar6 后：
push esi
call FUN_0043c930        ; 断肢对象生成（cdecl），可返回 NULL
mov [eax+0x104], ~uVar6  ; ← 崩溃：未判返回值!
```

崩溃处原始字节（dump 中 code bytes 吻合）：

```
56                       push esi
89 86 04 01 00 00        mov [esi+0x104], eax
e8 6b 99 03 00           call 0x43C930          ; ← 0x402FC0
33 c9                    xor ecx, ecx           ; ← 0x402FC5
f7 d3                    neg edx
89 98 04 01 00 00        mov [eax+0x104], ebx   ; ← 0x402FC9 崩溃
```

### 补丁 2

hook `0x402FC0` 处 5 字节 call（`E8 6B 99 03 00`）改为 `E9 rel32` 跳 cave `0x5E4972`：

- **hook**：raw `0x002FC0` → `E9 AD 19 1E 00`（跳 `0x5E4972`）
- **cave**：raw `0x1E4972`（VA `0x5E4972`），22 字节：

```
E8 B9 7F E5 FF           call 0x43C930          ; 原断肢生成调用
85 C0                    test eax, eax
74 05                    je   +5                ; NULL → 走跳过路径
E9 45 E6 E1 FF           jmp  0x402FC5          ; 非空 → 原续点（xor ecx,ecx 起）
83 C4 04                 add esp, 4             ; 平衡 push 的参数（cdecl 调用者清栈）
E9 7D E6 E1 FF           jmp  0x403005          ; 跳过整个断肢初始化块，到块尾续点
```

跳过路径直接落到块尾 `mov eax,[ebp+8]; test eax,eax; je...`（`0x403005`），
即模型部件记录缺失时**放弃生成断肢对象**，不影响正常断肢流程。

## 四、补丁汇总

| 补丁 | hook 点 (VA) | 原字节 | 新字节 | cave (VA) | 修复 |
|---|---|---|---|---|---|
| 1 | `0x40DA6A` | `83 B8 3C 01 00` | `E9 C3 6E 1D 00` | `0x5E4932` (28B) | `FUN_0040d9f0` 对 `[T+0x38]` 缺判空 → 读 `NULL+0x13C` |
| 2 | `0x402FC0` | `E8 6B 99 03 00` | `E9 AD 19 1E 00` | `0x5E4972` (22B) | `FUN_00402ca0` 对 `FUN_0043c930` 返回值缺判空 → 写 `NULL+0x104` |

Code cave 位于 `.text` 段末尾 `0x5E4932` 起的全零空洞（共 1742 字节），
无需新增节、无需改重定位表，原 exe 其余部分不动。

成品：`DFBHD_patched.exe`（补丁 1 + 补丁 2 合并版），直接替换游戏根目录原 exe 即可。

### 验证结果（对成品 exe 只读校验）

```
P1 hook 0x40DA6A -> cave 0x5E4932   ✓
P1 cave back     -> 0x40DA7A        ✓
P2 hook 0x402FC0 -> cave 0x5E4972   ✓
P2 call target   -> 0x43C930        ✓
P2 resume        -> 0x402FC5 (33 c9 f7 d3 89 98)  ✓ 与 dump 吻合
P2 skip          -> 0x403005 (8b 45 08 85 c0 74 0a c7) ✓ 与 dump 吻合
```

## 五、遗留风险

断肢是半成品功能，全 exe 中约 **70 处**代码站点依赖同一门控标志
（`test byte [r+0x20], 1` 形态），不排除存在第三处缺判空的崩溃点。
若再出现崩溃：

1. 保留 SYSDUMP.TXT；
2. 用 `文件偏移 = EIP − 0x400000` 在 exe 中定位崩溃指令；
3. 对照 dump 中 code bytes 确认上下文；
4. 按本报告相同的 hook + cave 模式补判空即可。

欢迎提交新的 dump 与复现条件（地图、单位、武器）以便继续排查。
